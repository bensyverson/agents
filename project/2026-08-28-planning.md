# Writing a plan

*2026-08-28.* How a plan is written here and how it becomes leaves. `project/agents/jobs.md` is the tracker's mechanics; `project/agents/delegation.md` is running agents; this is the thinking that comes before either. [2026-08-28-practice-plan.md](2026-08-28-practice-plan.md) is the running example — read it beside this, for its structure rather than its subject. Written as a dated doc to converge in use; it becomes a `planning` file module once a few plans have been written against it.

## What a plan is for

**A plan converges on decisions; the tracker holds work.** Every section exists to make a decision reviewable — what we chose, what else was on the table, what we knew when we chose. Once the decisions are ratified, the work they imply goes to `job` and the doc stops being read except to answer "why is it this way".

**The doc is the durable record; leaves are the schedule.** A leaf is closed and gone within days. The doc stays in `project/`, gets linked from gotchas, from later plans, and from the umbrella's description. Anything worth rereading in three months belongs in the doc, not in a leaf description.

**It has two readers.** The user, ratifying the decisions before any work starts, and an agent with fresh context that will execute one wave and has read nothing else. The first reader wants the Decisions section; the second wants Verified facts, its wave's file ownership, and its criteria.

## When to write one

**Write a plan when the work spans more than one session, more than one agent, or turns on a decision the user must ratify.** Those are the three cases where the thinking outlives the doing: a second session needs the reasoning restated, a second agent needs the boundaries written down, and a ratifiable decision needs something to ratify.

**Otherwise a leaf with criteria is enough.** One scoped change with a clear definition of done needs no document — `job add <parent> "<title>" --criterion …` carries it. A plan for that costs a review round and buys nothing.

**A plan is not the analysis it acts on.** If the open question is still "how should this work", that is a separate dated doc — an assessment, a gap analysis, a proposal — and the plan is what we decided to do about it. The practice plan's first line does exactly this: it names the assessment, the review session that settled it, what landed already, and what is out of scope.

## The shape

### Goal

**One paragraph: what changes, and what "done" means.** Done is a state of the world, not a list of tasks — "every managed repo renders the `jobs` module and the seven retired gotchas are deleted" beats "write the jobs module". If the paragraph cannot say when to stop, the plan is not ready to import.

**Date the reasoning.** Name the source doc and the day the decisions were taken, so a later reader knows what the decisions were made against.

### Verified facts

**Facts you measured, each with the command that measured it.** Not a context dump: the counts, timestamps and invariants an agent would otherwise get wrong or burn a turn rediscovering. `agents status` per repo and a `git log` count of gotcha deletions are what made the practice assessment's table arguable rather than impressionistic.

**Keep assumptions in their own list, labelled.** "Alpha's `gotchas.md` has 47 entries, 0 ever deleted" is a fact; "most of them are harness facts, not project traps" is an assumption until someone counts. A brief that presents the second as the first sends an agent to build on it.

**A fact that no longer reproduces has expired.** Re-run the command before dispatching a wave that depends on one; a plan written a week ago is not evidence about today's tree.

### Options weighed

**Diverge, then converge: the alternatives, the recommendation, and what it costs.** A plan that shows only the chosen path cannot be reviewed — the reviewer has nothing to disagree with. Two or three genuine alternatives, a sentence each on why they lost, and the cost of the winner stated plainly.

**Only where the choice was close.** Where there is one idiomatic answer, take it and record it as a Decision; manufactured options waste the reviewer's attention, which is the scarce thing.

**Record what was decided against, and where it went.** Work considered and dropped goes to `project/backlog.md`, not into a leaf and not into silence.

### Decisions

**Numbered, one sentence each plus its why. This is the section a reader returns to.** It is the plan's contract: every wave, every leaf and every criterion downstream implements a decision here and nothing else. The practice plan's Decisions run one bolded lead per decision — the verb or the new surface — then the rule and its consequence.

**A decision no wave implements is an idea, not a decision.** Cut it, or file the work it implies.

**Scope exclusions are decisions too.** "`design-process` is a WIP and out of scope" belongs here, because it is the line an agent would otherwise cross.

### Waves

**Waves are dependency order, not effort or theme.** A wave is the set of leaves whose blockers have all landed, so it can run in parallel. If two leaves in a wave block each other, the wave is wrong.

**Every wave states the file surface of each of its leaves, and no two leaves in a wave may share a file.** A worktree stops one agent's red tests from breaking another's build; it does nothing about merge conflicts. Map the surfaces first, parallelize the disjoint set, and for the contended set either pre-carve the seam in a prep commit, reserve the file to one writer while the others code against its interface, or serialize. A shared file every leaf wants a line in — a route table, a nav block — is named in the plan and owned by exactly one leaf; the rest declare `blockedBy` on it.

**Say what each wave ends with.** Sync, commit, review — the practice plan closes its Decisions with "every wave ends with `make sync` and a commit per managed repo". A wave whose ending is not written down ends whenever an agent thinks it has.

**Waves are for the reader's model of the work.** The tracker enforces the actual order through `blockedBy`; a wave heading that contradicts a `blockedBy` edge is a bug in one of them.

### Criteria

**One checkable sentence per criterion, on the leaf.** Checkable means someone other than the author can run or read something and say yes or no: "`agents check` exits 0 silently on a clean repo and 1 with a message on a stale one" is checkable; "the check verb works well" is not.

**Two to four per leaf.** They are the definition of done, and `job done` refuses to close over a pending one, so a criterion nobody will mark is friction with no payoff.

**A criterion that names a file or a command is worth two that name a feeling.** Where a leaf changes shared rules, one criterion should cover the downstream effect — the pinned hash test, the no-op sync, the deleted gotchas.

## Turning the plan into leaves

**The plan ends with one fenced YAML `tasks:` block, imported with `job import <file>` — `--dry-run` first, always.** `job schema` prints the grammar. The shape is one umbrella, a container per wave, and work leaves under each container:

```yaml
tasks:
  - title: <the goal, as a title>
    desc: >-
      Umbrella for project/<date>-<name>.md. <why this work exists, in the plan's own words> <what every wave ends with>
    labels: [<campaign label>]
    children:
      - title: "Wave 1: <name>"
        children:
          - title: <one unit of work>
            ref: <short-handle>
            blockedBy: [<ref from an earlier wave>]
            desc: >-
              <the why, for an agent with fresh context: what to change, what it replaces, the fact that motivates it, the files it owns>
            criteria:
              - "<checkable sentence>"
```

**`ref` is a handle local to the import; `blockedBy` resolves against refs first, then verbatim titles, then existing IDs.** Give a `ref` to anything another leaf blocks on and to nothing else — an unreferenced handle is noise.

**`desc` carries the why, for an agent that has read nothing.** It restates the motivating fact, names what the change replaces, and lists the files the leaf owns. What stays in the doc is everything shared: the options weighed, the facts table, the cross-wave file map, the reasoning behind a decision several leaves depend on. Duplicating a Decision's sentence into a `desc` is right; duplicating the whole Options section is not.

**A leaf description is still not a brief.** An agent that cannot read the tracker cannot read what is in it, and a worktree has no `.jobs.db` of its own — anything load-bearing is restated in the prompt or in a committed file.

**Cross-reference both ways.** The umbrella's `desc` names the doc by path; after the import, the doc's header line names the umbrella's ID. The practice plan's block imported as umbrella `iZ7pQ`, and that pair of pointers is what makes "why does this leaf exist" answerable from either end.

## Review before import

Run this over the block before `job import --dry-run`, and over the dry run's output after:

- **Every leaf has a parent.** A top-level entry without `--parent` mints a root, and roots render as peers of whole projects.
- **Every leaf has criteria**, and each one is checkable by someone who did not write it.
- **Every leaf's file surface is named, and no two leaves in the same wave collide.** Where they must, one owns the file and the other is `blockedBy` it.
- **Every `blockedBy` resolves**, and none of them point sideways within a wave.
- **Every fact in Verified facts is actually verified** — the command is recorded, and it still reproduces today.
- **Every Decision is implemented by some leaf**, and every leaf implements some Decision.
- **Each leaf is a unit of work, grouped by the files it touches** — not one leaf per line of feedback. Per-leaf overhead is a brief, a worktree, an integration and a contention negotiation; merge cost decides the split, not item count.
